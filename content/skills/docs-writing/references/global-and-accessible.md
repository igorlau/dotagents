# Global and accessible writing

Rules for the [`docs-writing`](../SKILL.md) skill that help readers who use translation tools, read in a second language, or use assistive technology.

## Global audience

- Use simple words: "start", not "commence"; "so", not "consequently"; "some" or "many", not "a number of".
- Prefer one-word verbs to phrasal verbs, except standard terms such as "set up" and "sign in".
- Use each word in its primary sense, and don't use the same word as a noun and a verb close together.
- Use subject-verb-object order, and keep the subject and verb near the start of the sentence.
- Keep helper words that make structure explicit: "that", "then", "of". Write "Update the rules that you defined", not "Update the rules you defined".
- Write "if X, then Y" in technical conditions.
- Place "only" directly before the word it modifies.
- Use no more than two nouns to modify another noun.
- Replace "using" with "by using" or "that uses" when the meaning is unclear.
- Avoid idioms, metaphors, humor, slang, pop culture, sports references, and holidays.
- Use a diverse set of names in examples, and use example domains such as `example.com`.
- Address the reader as "you". Use "users" only for the people who use the software that the reader builds.
- State what the reader can do instead of what they can't.

## Accessibility

- Break text into short paragraphs, headings, and lists. Put the key information in the first sentence of each paragraph.
- Keep sentences under 26 words. Avoid double negatives and exceptions to exceptions.
- Define acronyms at first use, and again if they appear rarely.
- Write link text that makes sense out of context, because screen reader users often navigate by links alone.
- Give every image alt text that conveys its purpose. Use empty alt text for decorative images.
- Never put information only in an image, and never use images of text, code, or terminal output.
- Don't rely on color, size, position, or shape alone. Pair each with a text label.
- Refer to UI elements by their labels, not by appearance ("the bell icon") or position ("on the right").
- Use "and", not "&", except in UI labels and code.
- Don't rely on punctuation alone to carry meaning, because some screen readers skip it.
- Don't insert hard line breaks inside sentences.
- Introduce every table, and use header cells for the first row or column only.
- Provide captions or transcripts for audio and video, and avoid flashing content.

## Inclusive language

- Use gender-neutral language. Use "they" for a person of unknown gender.
- Use people-first or identity-first language as each community prefers. Don't describe people without disabilities as "normal" or "healthy".
- Replace terms with violent, ableist, or oppressive connotations. See the inclusive language table in [`word-list.md`](word-list.md).
- When code requires a non-inclusive term, use it only in code font, and use the inclusive term in prose.
